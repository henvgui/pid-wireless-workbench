## 已修复的问题

| 问题 | 原来的影响 | 修复 |
|---|---|---|
| 共享库入口对第二条请求缺少内部保护 | 当前主机外层已有串行保护，更新前的实际密集 USB 测试也通过，未复现用户链路中的覆盖故障；其他调用入口若绕过外层保护则存在风险 | 加固共享库：保留当前请求及未取走回复；客户端继续按单请求方式重试 |
| 传输阶段失败后保留 Receiving/Ready | 目标还未擦除，但 H2 可能一直处于烧录暂停状态 | ERASE 尚未发送时，失败清理主动释放本次暂存；释放失败明确记入 journal。ERASE 一旦发出，即使 ACK 丢失也不自动中止或重擦 |
| 后台服务断开后只反复读取 | 窗口可能一直报连接错误，无法自行恢复 | 合并并发服务启动；恢复本地服务，重建接收会话，保留已显示日志；不重放写入请求 |
| 断线时按“关闭串口”可能重新开始重试 | 用户主动停止后又自动重连 | 本机停止优先；远端关闭无法确认时明确显示“远端关闭未确认” |
| GUI 和 Keil 使用不同凭据查找方法 | 服务位于 Codex 应用数据目录时，CLI 能用而 GUI 找不到/读错 token | CLI 先验证有效凭据，只返回其文件路径供 GUI 读取，不输出 token 内容 |
| 串口状态残留旧错误及旧读取时间 | 恢复后诊断信息仍像故障中 | 成功读取清除过期错误，新会话清除旧读取时间；修正 stale_request 的恢复分类 |
| 查询失败后仍保留绿色“已连接”标题 | 容易把过时状态当作实时连接 | 查询失败显示“连接状态待确认” |
| 回传原生测试沿用 192 字节分块 | 测试与保留 128 字节的实际 echo 协议不符 | 测试使用明确的 kLegacyChunk；实际 echo 协议和应用不改变 |
| OpenAPI 文字把 F407 SWD 写成仅 VGT6 | AI 可能误判已适配的 VET6 不可用 | 与芯片目录一致：VET6 已有实板验收，VGT6 待实板验收 |

## 保留的边界

- 当前 F407 原程序仍以 USART1 115200/8N1 打印，未接入主机 PID/RUN/STOP 的应用层协议，原 TIM6 源码仍固定 PWM=800；主机 STOP 或从机 ACK 不能当成目标电机已停机的确认。本轮只重烧已验证的同一镜像用于回归，没有修改目标业务源码，结束后保持目标暂停。
- 没有硬件流控时，持续满速打印或长时间断线仍可能填满缓冲；明确报告 gap/dropped/UART 错误，不能承诺任何距离和负载下绝不丢数据。
- 发送去重针对当前有效会话；跨后台/从机断电的业务恰好执行一次，需要目标应用的事务编号和结果查询。
- 本轮未重新布线、测量电压或复核 PCB；本报告是软件代码及测试检查，不是硬件重新验收。
